# MeetingTutor 開發手冊

> 本手冊定義目前 MVP 的實作方式與後續擴充邊界。API Key 可由使用者選擇保存在瀏覽器 `localStorage`，但不應把任何秘密值提交到 repository。

## 1. 建議技術基線

- 前端：TypeScript + React + Vite。
- 瀏覽器轉錄：Transformers.js／Whisper 類模型，在 Web Worker 執行；UI 預設 `Xenova/whisper-base`（英文為 `Xenova/whisper-base.en`），使用者可切換到 tiny；模型檔依實際授權與 bundle 大小決定是否由 Hugging Face CDN 下載。
- 音訊：Web Audio API、`MediaRecorder`；音訊解碼與取樣率轉換放 Worker／AudioWorklet。
- PDF：pdf.js（打包進建置產物或受控的本地資產），文字檔使用 File API。
- 本機資料：IndexedDB 儲存非秘密專案資料；目前 UI 以 Provider 分開將 API Key 保存於瀏覽器 `localStorage`，並提供清除按鈕。不可將 Key 匯出或提交。
- 測試：Vitest（單元）、Playwright（瀏覽器流程）、schema fixture（LLM 輸出驗證）。
- 部署：GitHub Actions 建置後發佈 GitHub Pages；所有 runtime asset 使用相對路徑。

若團隊希望降低依賴，也可以將 UI 改為 vanilla TypeScript，但不得因此把 provider、轉錄、文件渲染與安全檢查混在單一檔案。

## 3. 開發順序

1. 先建立 `MeetingProject` schema、fixture 與匯入／匯出，讓所有輸出共享同一事實來源。
2. 建立本地音訊與假轉錄 adapter，先完成逐字稿編輯 UI，再接真正模型。
3. 建立 provider adapter 介面與 mock server／fixture，完成測試、模型清單與錯誤映射。
4. 加入 PDF／文字抽取與詞彙確認流程。
5. 建立結構化生成 schema、prompt 版本與 diff review。
6. 先以固定 fixture 渲染四份 Markdown，再渲染 A4 HTML；最後接 UI 下載。
7. 加入真實 provider 的 opt-in 整合測試、GitHub Pages build 與列印檢查。

不要先做「一個按鈕全部完成」的流程；每個中間結果都要可預覽、可取消、可復原。

## 4. Provider adapter 契約

實作時以介面隔離各家 API 差異，概念契約如下（僅規格，不是目前要執行的程式碼）：

```ts
interface ProviderAdapter {
  id: 'openai' | 'xai' | 'google' | 'cgu';
  validateConfig(config: ProviderConfig): ValidationResult;
  testKey(secret: SecretRef, config: ProviderConfig): Promise<TestResult>;
  listModels(secret: SecretRef, config: ProviderConfig): Promise<ModelInfo[]>;
  generateText(input: GenerationInput, secret: SecretRef, config: ProviderConfig): Promise<StructuredResult>;
  sanitizeError(error: unknown): UserFacingError;
}
```

實作規則：

- 所有 HTTP 呼叫都要有 timeout、取消訊號、重試上限與 rate-limit 訊息。
- `sanitizeError` 不得回傳 Authorization header、URL query 中的 Key 或完整請求 body。
- `listModels` 不可用硬編碼清單冒充成功；若 provider 不支援列舉，必須讓 UI 明示「請手動輸入模型」並記錄限制。
- 生成前顯示「會送出的資料摘要」；使用者取消即不呼叫。
- 每個 provider 都要有 mock fixture；真實整合測試使用本機環境變數，不得把 Key 寫入測試檔。

### CGU 特別流程

目前 UI 預填 CGU base URL `https://air.cgu.edu.tw/cgullmapi/v1`。仍要以瀏覽器 DevTools 或 CGU 正式文件確認實際 network request，記錄 API URL、method、headers／body、成功／錯誤 schema、模型列舉方式、CORS 與服務條款。若沒有允許 GitHub Pages 的 CORS，MVP 不可自行繞過；待決策是由使用者提供相容 endpoint，或另建有明確安全邊界的 relay。

## 5. Prompt 與結構化輸出

Prompt 應拆成不可變的 system 規則、使用者輸入摘要、參考資料片段與輸出 schema。每次生成記錄 `promptVersion`，不要把整份 Key／隱私資料寫入紀錄。

### 5.1 修飾輸出 schema

```json
{
  "revisedText": "...",
  "changes": [{"from": "原文", "to": "修訂", "reason": "語句／術語", "confidence": "high|medium|low"}],
  "terms": [{"source": "...", "suggested": "...", "status": "confirmed|candidate|uncertain", "evidence": ["file#page"]}],
  "uncertainties": ["..."],
  "evidence": [{"claim": "...", "source": "transcript#segment-12"}]
}
```

schema 驗證失敗時只能進入「需重試／顯示原文」流程，不能把未驗證的自由文字直接寫成正式會議紀錄。

### 5.2 會議成果 prompt 規則

將附件 `AGENTS.md` 的固定格式轉為版本化提示與程式化檢查：決策狀態、`DEC-...`、`ACT-...`、待確認、禁止虛構、來源依據及三步驟順序。模型生成後再由 domain validator 檢查 ID、欄位與交叉一致性，不能只相信 prompt。

## 6. 參考資料處理

- 讀檔前檢查 MIME、副檔名、大小上限與檔案數上限。
- PDF 抽取結果保留頁碼；無文字層的掃描 PDF 在 MVP 顯示「需要 OCR」，不可假裝已讀取。
- 參考資料在本機切成帶來源定位的 chunks；只將與當前段落相關的片段送給 LLM。
- 來源檔與抽取文字可以存 IndexedDB，但使用者必須能一鍵刪除專案資料。
- 任何輸出 HTML 皆使用 escape／安全 DOM 建構；禁止 `innerHTML` 直接放入未清理的逐字稿。

## 7. GitHub Pages 部署

1. `main` 分支只接受通過 lint、typecheck、unit、build 的變更。
2. GitHub Actions 建置靜態資產，部署到 Pages artifact；不在 workflow 寫入 provider Key。
3. SPA 路徑使用 hash routing 或 Pages fallback；模型與 worker 路徑用 `import.meta.env.BASE_URL`。
4. 加入固定的安全標頭／meta CSP（依實際模型下載來源調整），並禁止未知第三方 script。
5. 部署後以無痕視窗檢查：首次載入、硬重新整理、無網路開啟已下載的 A4 HTML、WebGPU 不可用、麥克風拒絕。

## 8. 本機開發與秘密管理

規劃中的常用指令（真正的 package scripts 待實作時定案）：

```text
pnpm install
pnpm dev
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
pnpm build
```

禁止：把 Key 放在 `.env` 後提交、把 Key 放在 URL、在 console 印出 request headers、以真實會議資料做公開 fixture。瀏覽器 `localStorage` 僅作使用者明確選擇的本機保存位置，需提供清除流程，不得匯出或同步到 repository。真實整合測試使用本機未追蹤的環境變數，並在測試後清除。

## 9. 測試策略

- 單元：ID 產生、日期／狀態判讀、HTML escape、schema、資料外送摘要、錯誤遮罩。
- Provider contract：四家 adapter 的 mock success／401／403／429／5xx／CORS／malformed response。
- 轉錄：空音訊、長音訊、中文、時間碼、取消、Worker 例外、模型下載中斷。
- 參考資料：多頁 PDF、掃描 PDF、亂碼、重複檔名、超過上限、惡意 HTML／script 文字。
- 生成：專有名詞保護、不同意見、未決事項、缺主責／期限、模型輸出 schema 錯誤。
- 視覺：A4 直式、表格換行、跨頁標題、列印時隱藏按鈕、無 CDN 開啟。
- 互動驗收：硬體檢測不阻擋流程；文字校正逐項提供維持／同意／自訂，紅色標示建議詞且預設同意。
- 人工驗收：至少一段含人名／專案名的繁中會議，逐字稿原文、修訂 diff、四份輸出與 A4 PDF 逐項核對。

## 10. 版本與變更原則

- 任何 prompt、輸出 schema、ID 規則或 A4 欄位變更都要更新版本與 fixture。
- Provider API 變更先更新 adapter contract test，再更新 UI。
- 不因模型「看起來比較順」就移除原文或待確認標記。
- 發布前將 `docs/01_產品規格書.md` 的驗收條件轉成可勾選的 release checklist。
